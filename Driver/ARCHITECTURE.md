# Архитектура интеграции модулей JobSeeker

Постоянное описание общей архитектуры, восстановленное из удалённого
`Driver/API_PLAN.md` с учётом последующих договорённостей. Правила относятся
ко всем Java-модулям JobSeeker, не только к каталогам внутри Driver, и должны
соблюдаться при реализации и изменении их API и CLI. Это не план работ и
не описание будущего UDS-сервера. Конкретные операции перечислены в
[Driver API](api/README.md) и документации модулей.

## Два самостоятельных пути

```text
Java / JavaFX -> DriverApi -> API нужного модуля
Общий CLI    -> CLI нужного модуля -> API того же модуля
```

Каждый модуль сохраняет собственные программный API и CLI, доступные
независимо от фасада. Java-клиент может вызвать API модуля напрямую;
самостоятельный `main` модуля вызывает его CLI-обработчик.

## Программный API и фасад

API модуля выполняет бизнес-операции и возвращает Java-результаты.
Разбор команд, консольный вывод результата и транспорт находятся снаружи API.

`DriverApi` — единый многоразовый программный фасад над API модулей.
Программные операции соответствуют поддерживаемым действиям общего CLI.
Фасад непосредственно делегирует вызовы API, не вызывает CLI и не реализует
бизнес-логику модулей. Последовательностью сбора и анализа по-прежнему владеет
`WorkflowOrchestrator`, а не фасад.

Фасад возвращает существующие DTO и строки без JSON-преобразований,
дублирующих DTO и ручного перестроения результатов. Он не обращается
к Python вместо существующих адаптеров модулей.

Maven-зависимости фасада направлены к модулям, которыми он пользуется.
Обратные зависимости модулей на `Driver/api` и циклы недопустимы.
Общий код Tools не зависит от своих потребителей.

## CLI модулей и общий CLI

CLI-обработчик модуля — единственное место разбора его команд и аргументов,
преобразования их в вызовы API, форматирования результата и определения
кодов завершения. Он переиспользуем внутри JVM и не вызывает `System.exit()`.

Общий CLI только выбирает обработчик модуля и передаёт ему аргументы
в ожидаемом формате. Он не повторяет проверку аргументов, бизнес-логику,
преобразование результатов или сериализацию.

Оба фасада вызывают модули в той же JVM, без `ProcessBuilder` и дочерних
Java-процессов. Это правило делегирования не запрещает модулю использовать
внешний процесс там, где он нужен его собственной операции.

## Результаты и консольная оболочка

Консольная оболочка — тонкий `main`: вызывает CLI-обработчик и завершает
процесс с полученным кодом. Допустимы оба варианта:

- CLI-обработчик сам выводит результат в stdout/stderr и возвращает код
  завершения; `main` не печатает результат повторно.
- CLI-обработчик возвращает ответ вызывающему; `main` печатает его и
  завершает процесс согласно контракту обработчика.

Выбор варианта не меняет разделения API и CLI и не требует переписывать
существующие обработчики ради единообразия вывода. Логи и диагностика
отделены от результата команды; существующие форматы и коды сохраняются.

DTO выводится прямой автоматической сериализацией, с сохранением его полей,
вложенных структур и аннотаций. Строка выводится напрямую, без JSON-обёртки
и DTO с одним текстовым полем. Сериализация принадлежит CLI модуля, а не
общему маршрутизатору или программному фасаду.

## Запуск и жизненный цикл

Создание API, обработчика команд и их закрытие принадлежат точке запуска
приложения. Обработчик получает готовый экземпляр API и не создаёт его заново
для каждой команды. Одноразовый `main` выполняет одну команду и завершает
процесс; долгоживущий вход переиспользует API. В GUI используются сервисы
работающей JVM, а не вызовы CLI через дочерний процесс.

`DriverApi` и сервисы переиспользуемы: обработчики прогресса конкретной
операции передаются в её вызове, а не закрепляются в конструкторах.
Это не требует сквозной передачи одного GUI-callback через все модули.

## Необязательный транспорт

UDS — отдельная возможность доступа к работающей JVM, пока не реализованная.
Она не является условием соблюдения описанной архитектуры и не разрешает
заранее добавлять серверные механизмы во все модули. Общий адаптер и открытые
вопросы описаны в [архитектуре Tools](../Tools/ARCHITECTURE.md);
реализация отложена в [бэклоге](../BACKLOG.md#next).

## Граница Java и Python через JPy

Часть логики исторически реализована на Python и сохраняется не только ради
совместимости: отдельные Python-функции удобно вызывать напрямую для локальных
экспериментов, тестирования и отладки, без пересборки Java-модулей и запуска
отдельной JVM. Поэтому переписывание этой логики на Java не является самоцелью.

Java gateway и Python bridge — тонкие межъязыковые адаптеры: преобразуют
параметры, результаты и ошибки и делегируют вызовы. Бизнес-правила и
последовательность действий операции находятся в программном API
соответствующего модуля, а не в адаптерах. Python-операции доступны
независимо от JPy и bridge.

JPy использует один встроенный интерпретатор Python на JVM. Его общая
инициализация выполняется через `JpyRuntime.ensureStarted(...)`;
закрытие отдельного gateway не останавливает общий интерпретатор.

Общие технические пути Python/JPy и `database.path` находятся в локальном
`Tools/runtime.properties` (пример — `Tools/runtime.properties.example`).
Параметры коллектора `java.executable`, `raw.directory` и `profile.directory`
остаются в `Driver/collector/java_linkedin/runtime.properties`.
