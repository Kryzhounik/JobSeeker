# Архитектура интеграции модулей JobSeeker

Постоянное описание общей архитектуры, восстановленное из удалённого
`Driver/API_PLAN.md` с учётом последующих договорённостей. Правила относятся
ко всем Java-модулям JobSeeker, не только к каталогам внутри Driver, и должны
соблюдаться при реализации и изменении их API и CLI. Это не план работ и
не описание будущего UDS-сервера. Конкретные операции перечислены в
[Driver API](api/README.md) и документации модулей.

## Учёт замечаний и задач

- Корневой [ISSUES.md](../ISSUES.md) — небольшие недочёты и проблемы,
  обнаруженные при ревью, анализе и другой работе, которые не требуют
  немедленного разбора. Это фиксация замечаний, не готовый план реализации.
- Корневой [BACKLOG.md](../BACKLOG.md) и бэклоги отдельных модулей — задачи
  и идеи с разным уровнем проработки; модульные относятся к своему модулю,
  корневой — к проекту в целом.
- GitHub Issues — обычно уже разобранные задачи с проработанным черновым
  планом выполнения. Сейчас туда поступают задачи от внешних агентов;
  полного переноса локальных замечаний и бэклогов в GitHub не проводится.

Эти места не взаимозаменяемы. Если из контекста непонятно, означает ли
«добавь в ишью» локальный `ISSUES.md` или GitHub Issues, агент уточняет место
до записи, а не выбирает его самостоятельно.

## Два самостоятельных пути

```text
Java / JavaFX -> DriverApi -> API нужного модуля
CLI          -> Tools CliRunner -> адаптер команд модуля -> API того же модуля
```

Каждый модуль сохраняет собственные программный API и CLI, доступные
независимо от фасада. Java-клиент может вызвать API модуля напрямую;
самостоятельный `main` запускает консольный путь своего модуля.

## Соглашение о форматах файлов

- `.ini` — параметры технического окружения: пути к Python, JPy, Java,
  локальным каталогам и другим ресурсам, необходимым для работы приложения.
- `.properties` — настройки поведения приложения и его модулей: лимиты
  вакансий, таймауты, включение функций и другие параметры выполнения.
- `.md` — документация, инструкции и промпты.
- `.txt` — свободный текст, наборы фактов и простые текстовые списки.
- `.json` — сериализованные доменные объекты, схемы и структурированный
  обмен данными.

Другие расширения для этих назначений допустимы при конкретной технической
необходимости. Приведение существующих файлов к конвенции подчиняется правилу постепенного
соответствия архитектуре из корневого `AGENTS.md`.

## Соглашение об именовании

Однотипные архитектурные роли во всех Java-модулях называются однотипно:

- `<Module>Api` — публичный программный вход модуля.
- `<Module>Adapter` — аннотированное описание команд и их привязка к API.
- `<Module>Cli` — консольная точка запуска с `main`.
- `CliRunner` в Tools — общий разбор аргументов, выполнение команд и вывод.
- `*Service`, `*Orchestrator`, `*Gateway`, `*Bridge` — внутренние компоненты
  согласно их фактической роли, а не альтернативные названия публичного API.

Соглашение не требует дополнительных обёрток или классов только ради имени.

## Программный API и фасад

API модуля валидирует входные данные, выполняет бизнес-операции и возвращает
Java-результаты. Ошибки сообщает исключениями своего контракта.
Разбор CLI-команд, консольный вывод
результата и транспорт находятся снаружи API. API не зависит от CLI и picocli.

`DriverApi` — единый многоразовый программный фасад над API модулей.
Программные операции соответствуют поддерживаемым действиям общего CLI.
Фасад непосредственно делегирует вызовы API, не вызывает CLI и не реализует
бизнес-логику модулей. Последовательностью сбора и анализа по-прежнему владеет
`WorkflowOrchestrator`, а не фасад.

Фасад возвращает существующие DTO и строки без JSON-преобразований,
дублирующих DTO и ручного перестроения результатов. Он не обращается
к Python вместо существующих адаптеров модулей.

Maven-зависимости фасада направлены к модулям, которыми он пользуется.
Обратные зависимости модулей на `Driver/api` и циклы недопустимы.
Общий код Tools не зависит от своих потребителей.

## CLI модулей и общий CLI

CLI-слой отвечает за разбор команд и аргументов, вызовы API, форматирование
результата и коды завершения. Он состоит из консольной точки запуска,
адаптера команд модуля и общего `CliRunner` в Tools.

Общий CLI Driver выбирает CLI-вход нужного модуля и передаёт ему аргументы.
Для запуска через Driver и самостоятельного запуска используется один
и тот же CLI-вход модуля. Driver не повторяет проверку аргументов,
бизнес-логику, преобразование результатов или сериализацию.

Самостоятельный консольный путь модуля:

```text
<Module>Cli.main -> Tools CliRunner -> <Module>Adapter -> <Module>Api
```

Точка запуска создаёт API и адаптер. Адаптер описывает команды и параметры
аннотациями picocli и делегирует вызовы API, возвращая его Java-результаты.
В адаптере нет самостоятельной или повторной валидации входных данных,
перехвата и преобразования исключений, сериализации или консольного вывода.

Общий runner через picocli разбирает аргументы, проверяет структуру команды,
наличие обязательных параметров и преобразует их типы. Значения и правила
операции проверяет API. Runner вызывает выбранный метод адаптера,
обрабатывает исключения, сериализует и выводит результат, определяет код
завершения. Он не выбирает модуль и не зависит от конкретных модулей или
их специфичных типов исключений. Правила обработки ошибок и коды завершения
описаны в [архитектуре Tools](../Tools/ARCHITECTURE.md).

Runner можно вызывать внутри JVM с готовым API через адаптер; консольную
точку запуска для этого вызывать не требуется.

Программный фасад и CLI-маршрутизатор вызывают модули в той же JVM, без `ProcessBuilder` и дочерних
Java-процессов. Это правило делегирования не запрещает модулю использовать
внешний процесс там, где он нужен его собственной операции.

## Результаты и консольная оболочка

Консольная оболочка — тонкий `<Module>Cli.main`: создаёт API и адаптер,
вызывает `CliRunner` и завершает процесс с полученным кодом. Runner выводит
результат; точка запуска не печатает его повторно. Только `main` вызывает
`System.exit()`; runner и адаптер переиспользуемы внутри JVM.

Логи и диагностика отделены от результата команды. Общие правила вывода и
кодов завершения описаны в [архитектуре Tools](../Tools/ARCHITECTURE.md).

DTO выводится прямой автоматической сериализацией, с сохранением его полей,
вложенных структур и аннотаций. Строка выводится напрямую, без JSON-обёртки
и DTO с одним текстовым полем. Сериализацию выполняет общий `CliRunner`;
адаптер возвращает обычный Java-результат вызова API.
Общий маршрутизатор Driver и программный фасад результаты не сериализуют.

## Запуск и жизненный цикл

Создание API, адаптера команд и их закрытие принадлежат точке
запуска приложения. Адаптер получает готовый API и не создаёт
его заново для каждой команды. Одноразовый `main` выполняет одну команду и завершает
процесс; долгоживущий вход переиспользует API. В GUI используются сервисы
работающей JVM, а не вызовы CLI через дочерний процесс.

`DriverApi` и сервисы переиспользуемы: обработчики прогресса конкретной
операции передаются в её вызове, а не закрепляются в конструкторах.
Это не требует сквозной передачи одного GUI-callback через все модули.

## Необязательный транспорт

UDS — отдельная возможность доступа к работающей JVM, пока не реализованная.
Она не является условием соблюдения описанной архитектуры и не разрешает
заранее добавлять серверные механизмы во все модули. Общий адаптер и открытые
вопросы описаны в [архитектуре Tools](../Tools/ARCHITECTURE.md);
реализация отложена в [бэклоге](../BACKLOG.md#next).

## Граница Java и Python через JPy

Часть логики исторически реализована на Python и сохраняется не только ради
совместимости: отдельные Python-функции удобно вызывать напрямую для локальных
экспериментов, тестирования и отладки, без пересборки Java-модулей и запуска
отдельной JVM. Поэтому переписывание этой логики на Java не является самоцелью.

Новую самостоятельную логику предпочтительно реализовывать на Java.
Существующую целостную Python-операцию следует естественно дорабатывать на
Python, если изменение относится к её ответственности. Например, добавление
поля в её результат не требует отдельного Java-кода, дополняющего этот результат.
При этом наличие Python-операции не является основанием размещать в ней новый
самостоятельный компонент. Граница определяется ответственностями компонентов,
а не запретом расширять Python или стремлением сохранить всю логику на одном языке.

Java gateway и Python bridge — тонкие межъязыковые адаптеры: преобразуют
параметры, результаты и ошибки и делегируют вызовы. Бизнес-правила и
последовательность действий операции находятся в программном API
соответствующего модуля, а не в адаптерах. Python-операции доступны
независимо от JPy и bridge.

JPy использует один встроенный интерпретатор Python на JVM. Его общая
инициализация выполняется через `JpyRuntime.ensureStarted(...)`;
закрытие отдельного gateway не останавливает общий интерпретатор.

Общие технические пути Python/JPy и `database.path` находятся в локальном
`Tools/runtime.properties` (пример — `Tools/runtime.properties.example`).
Общий корень RAW
`raw.directory` находится в `Driver/collector/config/collector.properties`;
каждый источник сохраняет файлы в своём подкаталоге `<source>/pages/`.
