# Задание: единые Java API и CLI фасады JobSeeker

## Цель

Создать единую точку входа для внешних Java-клиентов и единую командную строку для всех существующих модулей JobSeeker.

**Принципиально: не создавать новую бизнес-логику, не дублировать существующие реализации и не разрушать самостоятельность модулей.**

Исходный репозиторий: `Kryzhounik/JobSeeker`.

Перед началом изучить актуальный `master`, существующие Java API, CLI-команды, Maven reactor и тесты. Ниже описана целевая архитектура; конкретные сигнатуры сверять с актуальным исходным кодом.

## Целевая архитектура

```text
                     External Java / JavaFX
                              |
                              v
                          DriverApi
                              |
                +-------------+-------------+
                |             |             |
                v             v             v
          Collector API  Orchestrator API  Other APIs
                ^             ^             ^
                |             |             |
          Collector CLI  Orchestrator CLI  Other CLIs
                ^             ^             ^
                |             |             |
                +-------------+-------------+
                              |
                          API CLI
```

Здесь имеются два самостоятельных пути:

**Программный путь:**

`External Java → DriverApi → Module API`

**Командный путь:**

`API CLI → Module CLI handler → Module API`

API CLI непосредственно вызывает обработчик CLI нужного модуля в той же JVM. Не запускает дочерний Java-процесс и не парсит повторно аргументы соответствующего модуля.

`DriverApi` непосредственно делегирует вызовы Java API модулей. Не вызывает их CLI.

Каждый модуль сохраняет собственные Java API и CLI, которыми можно пользоваться независимо от фасада.

# Этап 1. Подготовка CLI модулей для повторного использования

## Проблема

Сейчас у каждого модуля собственная точка входа `main(String[] args)`.

Некоторые из них вызывают `System.exit()`, что делает непосредственный вызов `main()` из общего CLI небезопасным: ошибка отдельной команды может завершить всю JVM.

В то же время именно внутри этих CLI уже реализованы:

- разбор аргументов;
- преобразование аргументов в Java-типы;
- вызов соответствующего Java API;
- сериализация результата или вывод строки;
- диагностика и правила вывода в stdout/stderr;
- коды завершения.

Эту логику нельзя дублировать в общем CLI.

## Требуемое изменение

В каждом существующем CLI выделить переиспользуемый обработчик команд, например:

```java
public static int execute(String[] args);
```

Название может быть другим, если лучше соответствует существующему коду.

Контракт обработчика:

1. Принимает аргументы в формате существующего CLI.
2. Выполняет ту же операцию, что и раньше.
3. Выводит тот же результат в stdout/stderr.
4. Возвращает код завершения.
5. **Не вызывает `System.exit()`**.
6. Не требует запуска отдельного процесса.

Собственный `main()` модуля остаётся тонкой оболочкой:

```java
public static void main(String[] args) {
    int exitCode = execute(args);
    if (exitCode != 0) {
        System.exit(exitCode);
    }
}
```

Это пример организации, а не требование механически заменить существующий код.

Сохранить существующую обработку исключений, логирование, `ProcessLog`, `CliOutput`, перенаправление Python stdout и вывод прогресса.

В частности, проверить:

- `Driver/collector/java_linkedin/.../Main.java`
- `Driver/orchestrator/.../Main.java`
- `Applier/.../Main.java`
- `ChatEvaluatorRunner.main()`

У ChatEvaluator CLI и Java API сейчас находятся в одном классе. Разделять их необязательно, достаточно сделать CLI-обработчик переиспользуемым.

### Проверка этапа 1

Старые исполняемые JAR и их команды работают по-прежнему.

Вызов обработчика непосредственно из Java работает без `System.exit()`.

Сохраняются исходные stdout, stderr, коды завершения, диагностические сообщения и форматы результатов.

При ошибке обработчик возвращает соответствующий код, а не завершает JVM.

**Не менять бизнес-логику модулей и форматы CLI ради этого этапа.**

# Этап 2. Создание Maven-модуля фасада

Создать отдельный модуль:

```text
Driver/api/
    pom.xml
    src/main/java/com/seeker/api/
        DriverApi.java
        Main.java
```

Добавить его в reactor `Driver/pom.xml` и Maven dependency management.

Зависимости нового модуля направлены вниз:

```text
api
  ├── workflow-orchestrator
  ├── linkedin-collector
  ├── applier
  └── chat-evaluator
```

Не добавлять обратных зависимостей из существующих модулей на `api`.

Фасад должен собираться в отдельный тонкий исполняемый JAR с использованием существующей инфраструктуры `libs/` и Maven manifest classpath.

## 2.1. Java-фасад: DriverApi

`DriverApi` — публичный Java-класс, объединяющий существующие программные операции.

Базовый набор определяется существующими CLI-командами. Для каждого поддерживаемого CLI-действия должен быть соответствующий метод Java-фасада.

Предполагаемые методы:

```java
public LoginResult login();

public CollectionReport collectBatch();

public WorkflowResult processBatch(String source);

public WorkflowResult processUrls(String... urls);

public WorkflowResult resume(String runId);

public StageResult jobFacts(
    String runId,
    String source,
    List<ScopeItem> scope
);

public StageResult finishAnalysis(
    String runId,
    String source,
    List<ScopeItem> scope
);

public ApplierRunner.Result prepareApplication(String url);

public String evaluateWithChatGPT(String url);
```

Это предварительный перечень. Проверить существующие сигнатуры и, где возможно, использовать их без изменений.

В частности, `StageResult` и два соответствующих метода Orchestrator сейчас имеют package-private доступ. Для вызова из отдельного Maven-модуля потребуется обеспечить их публичную доступность.

**Не создавать дублирующие DTO.** Использовать существующие типы результатов соответствующих модулей.

Фасад не должен:

- реализовывать этапы workflow;
- самостоятельно выполнять фильтрацию или анализ вакансий;
- обращаться к Python вместо существующих JPy-адаптеров;
- самостоятельно разбирать JSON результатов;
- формировать новые версии `CollectionReport`, `WorkflowResult` или других DTO.

Всю последовательность сбора и анализа по-прежнему определяет `WorkflowOrchestrator`.

### Конфигурация и прогресс

`DriverApi` должен получать корень проекта (`Path projectRoot`) и обеспечивать передачу callback прогресса коллектора.

Использовать существующий механизм `Consumer<CollectionProgress>` — не вводить отдельный формат прогресса.

Не выполнять дорогостоящие операции, запуск браузера или анализ вакансий просто при создании фасада.

Для ChatEvaluator проверить существующее использование `seeker.projectRoot`. Если для корректной работы фасада требуется передача корня проекта, предпочтительно добавить перегрузку с явным `Path`, сохранив прежний `run(String url)`.

Не менять глобальные свойства JVM без необходимости.

## 2.2. CLI-фасад

Создать единый исполняемый CLI, например:

```text
java -jar Driver/api/job-seeker-api.jar <command> [args...]
```

Предлагаемая маршрутизация:

| API CLI | Обработчик существующего модуля |
|---|---|
| `login` | Collector CLI `login` |
| `collect-batch` | Collector CLI `collect-batch` |
| `process-batch linkedin` | Orchestrator CLI |
| `process-urls <url...>` | Orchestrator CLI |
| `resume <run-id>` | Orchestrator CLI |
| `job-facts ...` | Orchestrator CLI |
| `finish-analysis ...` | Orchestrator CLI |
| `apply <url>` | Applier CLI с передачей URL |
| `chat-eval <url>` | ChatEvaluator CLI с передачей URL |

`apply` и `chat-eval` — новые имена только для маршрутизатора: собственные CLI этих модулей сейчас принимают URL позиционным аргументом.

**Задача API CLI — исключительно маршрутизация.**

Он должен:

1. Распознать имя команды и выбрать CLI-обработчик.
2. Передать ему оставшиеся аргументы в ожидаемом формате.
3. Получить и вернуть код завершения.

Общий CLI **не должен** заново преобразовывать URL, ID и scope в Java-объекты, создавать JSON или повторять проверку аргументов, уже выполняемую CLI соответствующего модуля.

Пример:

```java
// Схематически
case "collect-batch" ->
    CollectorMain.execute(rest);

case "process-batch" ->
    OrchestratorMain.execute(argsForModule);

case "apply" ->
    ApplierMain.execute(rest);
```

Реальные имена классов и обработчиков подобрать на основе существующего кода.

Маршрутизатор не должен вызывать `main()` модулей, если тот способен завершить JVM.

Не использовать `ProcessBuilder` для обращения фасада к CLI модулей.

### Правило форматов результатов

Если метод Java API возвращает DTO, CLI выводит его прямой автоматической сериализацией.

Структура и поля JSON соответствуют DTO, включая вложенные структуры. Никаких ручных добавлений, удалений и перестроений полей на стороне фасада.

Существующие аннотации сериализации сохраняются.

Если Java API возвращает `String`, как ChatEvaluator, CLI выводит строку напрямую. **Не оборачивать её в JSON и не создавать DTO с одним текстовым полем.**

Вся сериализация остаётся у существующего CLI-обработчика модуля. API CLI не сериализует результат повторно.

### Проверка этапа 2

Проверить, что:

- `DriverApi` возвращает существующие Java DTO и строки без сериализации;
- API CLI передаёт аргументы нужному модулю;
- команды общего CLI и самостоятельные CLI модулей производят эквивалентные результаты;
- stdout, stderr и exit codes сохраняются;
- вызовы происходят внутри одной JVM;
- нет циклических Maven-зависимостей;
- модуль `api` собирается и запускается через `java -jar`.

Для маршрутизации предусмотреть автоматические тесты без обязательного запуска браузера, ChatGPT или Python.

# Этап 3. Интеграция JavaFX и окончательная проверка

После успешного завершения первых двух этапов перевести соответствующие программные вызовы JavaFX на `DriverApi`.

Сейчас JavaFX непосредственно использует:

- `LinkedInApplication` для сбора вакансий;
- `ApplierRunner` для подготовки заявок;
- `ChatEvaluatorRunner` для оценки через ChatGPT.

Нужно, чтобы эти операции вызывались через Java-фасад и сохраняли существующее поведение.

Не переводить их на общий CLI и не добавлять ненужные дочерние процессы.

Существующий диагностический режим Collector `collector.mode=process` можно сохранить. Он является отдельным намеренным способом запуска, а не обязательным маршрутом через фасад.

Сохранить:

- обновления прогресса через callback;
- асинхронность операций GUI;
- существующие статусы, окна и сообщения;
- порядок выполнения и обработку ошибок;
- существующий доступ GUI к базе через `ClientData`.

**`ClientData` в `DriverApi` не переносить.** Этот слой не входит в рассматриваемый набор CLI-операций.

## Финальные проверки

После реализации выполнить Maven-сборку и доступные автоматические тесты.

Отдельно проверить:

1. Все самостоятельные CLI модулей продолжают работать.
2. Общий CLI корректно делегирует каждую команду.
3. Java-фасад возвращает те же типы и данные, что соответствующие Java API модулей.
4. Нет дублирования парсинга и сериализации CLI.
5. JavaFX собирается с новой зависимостью и сохраняет прежнее поведение.
6. Ошибка отдельной CLI-команды не завершает JVM до возврата управления маршрутизатору.
7. Нигде не появились циклические Maven-зависимости.
8. Сохранились существующие форматы JSON и сырого текста.

Проверки, которые невозможно выполнить без авторизации LinkedIn, работающего браузера или реальных внешних сервисов, не симулировать как успешно пройденные. Отдельно указать, что именно проверено и что осталось непроверенным.

## Ограничения задачи

Не менять Python-модули, правила фильтрации, логику Orchestrator, БД и бизнес-алгоритмы, если этого не требует конкретная доказанная проблема интеграции.

Не вводить новые сервисные слои, универсальные обработчики бизнес-операций и общие DTO вместо уже существующих.

Не удалять самостоятельные CLI модулей.

Не менять формат результата ChatEvaluator.

Не проводить побочные рефакторинги.

**Работать последовательно: сначала переиспользуемые CLI-обработчики, затем фасад, затем интеграция JavaFX.**

После каждого этапа фиксировать отдельный коммит, выполнять доступные проверки и кратко перечислять изменения.

Окончательный результат: единый Java API и единый CLI над самостоятельными модулями, без дублирования логики, преобразования типов или сериализации.
