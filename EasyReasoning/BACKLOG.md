# EasyReasoning Backlog

## Семантические дубликаты вакансий

Приоритет: **MEDIUM**. Наблюдательный режим реализован; дальнейшие изменения
поведения пока не назначены.

После сбора и скриптовых фильтров сравнивать описания вакансий с одинаковыми
названием и компанией через EasyReasoning, перед дальнейшей фильтрацией и анализом.
Совпадение этих полей только отбирает
пары для модели. Разные города или страны и общие описания местного рынка труда
сами по себе не делают описания разными; не пытаться устанавливать, стоят ли за
публикациями разные реальные рабочие места.

Для обычного использования применять короткий английский промпт о существенных
различиях с ответом только `NO SUBSTANTIVE DIFFERENCES` или
`SUBSTANTIVE DIFFERENCES`, без объяснений. Длинный промпт использовать при разборе
конкретных обнаруженных ошибок. Предварительные эксперименты описаны в
[EXPERIMENTS.md](EXPERIMENTS.md).

Хранить связь дубликата с конкретной исходной вакансией. Каждая публикация
сохраняется в базе со своим текстом и данными объявления.

1. **Наблюдение внутри текущего прогона — реализовано.** Связь с исходной
   вакансией сохраняется в `source_jobs.semantic_duplicate_of`; сравниваются
   вакансии текущего батча. Оценки рассчитываются всем как обычно. Пользователь
   наблюдает и проверяет решения модели перед изменением этого поведения.
2. **Переиспользование оценки внутри прогона.** Если первый этап окажется
   успешным, не рассчитывать оценку дубликата повторно, а получать её от связанной
   вакансии текущего прогона, для которой оценка уже рассчитана.
3. **Поиск по всей базе.** Если второй этап окажется успешным, расширить поиск
   кандидатов с теми же компанией и названием на ранее сохранённые вакансии.
   Повторная публикация под новым LinkedIn ID, признанная моделью дубликатом,
   сохраняет собственный текст и использует уже рассчитанную оценку исходной
   вакансии.

Переход к следующему этапу — после оценки пользователем результатов предыдущего.

## Развитие пакетной операции и вариантов выполнения

Этапы 1–2 рефакторинга выполнены и прошли ревью: дедупликация выполняется
синхронно после сбора и принадлежит EasyReasoning. Ниже сохранены оставшиеся
этапы согласованного плана. Они не являются текущим поручением на реализацию.
Каждый назначается отдельно и завершается независимым ревью.
Resume в эти задачи не входит.

<a id="codex-luna"></a>

### 3. Подключение Codex/Луны

Добавить второй вариант выполнения внутри EasyReasoning через существующий
`com.seeker.codex.CodexClient` из Tools и `Driver/codex_proxy`, без нового
транспорта. Режим дедупа `off / qwen / luna` интерпретируется внутри операции;
оркестратор и Collector при переключении не меняются. Промпт и разбор ответа
общие для обоих backend. Выбор дедупа не переключает другие операции.

Параметры модели и reasoning задаются явно для этой операции, без молчаливого
наследования настроек основного анализатора. Конкретный профиль Luna уточнить
перед реальным проверочным вызовом. Автоматический fallback не добавлять.

Результат: один пакетный API работает во всех трёх режимах; `off` не обращается
к моделям, Luna использует существующий клиент и учёт вызовов. Проверить реальное
обращение к выбранной модели. Выбор backend сам по себе не гарантирует ускорения.

<a id="analysis-stream"></a>

### 4. Опционально: поток результатов параллельно анализатору

Начинать после замеров, если синхронный дедуп заметно задерживает анализ.
После окончания сбора EasyReasoning обрабатывает батч в фоне и выдаёт поток
готовых ID; анализатор читает его параллельно. Очередь и её завершение скрыты
внутри пакетного уровня EasyReasoning. При `off` все подходящие ID выдаются
без сравнения.

Результат: анализ начинается до окончания дедупа, ID не теряются и не выдаются
повторно, окончание потока однозначно. Сохранить существующую организацию анализа
батча и общий контекст оценивания; не запускать полный анализатор заново для
каждого ID. Исключение дублей и переиспользование оценок остаются отдельным
изменением поведения, описанным выше; очередь сама по себе его не включает.

<a id="scanner-worker"></a>

### 5. Опционально: Scanner и Worker

Зависит от этапа 4. Нужен, если медленные сравнения задерживают передачу вакансий,
для которых сравнение вообще не требуется.

Scanner проходит сохранённые вакансии: ID без кандидатов сразу направляет в
выходной поток, остальные — в очередь сравнений. Worker последовательно
сравнивает кандидатов, сохраняет связи и выдаёт ID согласно действующей политике
обработки дублей. Внешний потребитель читает единый поток параллельно обоим.

Контракт ошибок дедупа: отрицательный ответ, исключение или некорректный ответ
не препятствуют передаче вакансии в анализ; ошибки видимы и не записываются
как успешная проверка «не дубль». При зависании внутренний таймаут прекращает
сам запрос либо работу собственного зависшего локального процесса, отключает
проблемный backend до конца текущей обработки и выпускает непроверенные вакансии
дальше. Просто перестать ждать продолжающееся вычисление недостаточно.
Конкретный таймаут определить перед реализацией этапа.

Результат: сравнения не задерживают вакансии без кандидатов; ошибка или зависание
модели не блокируют остальные ID. Завершение выходного потока сообщается после
окончания Scanner и Worker и обработки их очередей.

<a id="collection-overlap"></a>

### 6. Опционально: работа параллельно Collector

Зависит от этапа 5 и практической необходимости перекрыть дедупликацию со сбором.
Запускать EasyReasoning до коллекции: он получает новые сохранённые вакансии
батча и предоставляет тот же поток результатов. Collector не вызывает дедуп
и не управляет его очередями.

Оркестратор управляет запуском и сообщает об окончании сбора. Временно пустая
очередь не означает завершения коллекции.

Результат: вакансии обрабатываются по мере сохранения, окончание сбора и
окончание потока различаются, Collector сохраняет независимость от дедупликации.
