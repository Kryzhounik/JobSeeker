# Архитектура ChatEvaluator

## Поток работы

`JavaFX GUI → ChatEvaluator → HTTP-проверка вакансии → при 429 проверка в браузере → существующий диалог ChatGPT → новый ответ → GUI`.

Проверочный вход по пункту 4:
`CLI (java -jar) → тот же ChatEvaluatorRunner.run(url) → тот же браузерный сценарий → stdout`.

По отдельному действию пользователя GUI передаёт URL выбранной вакансии.
ChatEvaluator читает адрес целевого диалога из своей настройки, отправляет
в диалог только URL вакансии, дожидается нового законченного ответа
и возвращает его текст. Правила оценки и контекст пользователя находятся
в самом диалоге.

GUI и CLI различаются получением входного URL и показом результата.
Логика оценивания, работа с браузером, настройками и ответом находится
в единственном общем `run(String vacancyUrl)`.

## Минимальный состав

- `ChatEvaluator/src/main/java/com/seeker/chatevaluator/ChatEvaluatorRunner.java`:
  обычный Java-класс с точкой входа `run(String vacancyUrl)`. Он читает
  настройку, работает с браузером и возвращает текст ответа. Для первой
  реализации достаточно одного класса; отдельные интерфейсы, фабрики
  и универсальная система работы с разными чатами не требуются.
  Существующий `main(String[] args)` оформить как тонкий CLI-адаптер:
  разобрать аргументы, вызвать тот же `run`, вывести ответ или ошибку
  и установить код завершения. Второй runner с браузерной логикой не нужен.
- `ChatEvaluator/pom.xml` по пункту 4: отдельная минимальная сборка запускаемого
  `ChatEvaluator/target/chat-evaluator.jar` с `Main-Class` и необходимыми
  runtime-зависимостями. Она компилирует исходники ChatEvaluator и напрямую
  подключает оригинальный `ManagedBrowser` из Applier и проверку вакансии из
  `Tools/src/main/java`. Исходники не копировать;
  `ApplierRunner`, JavaFX и jpy в CLI-сборку не включать.
- `Data/chat_evaluator/config.properties`: локальная настройка `chat.url`
  с предоставленной пользователем ссылкой на рабочий диалог. Для явно
  запрошенной живой проверки значение временно заменяется ссылкой на отдельный
  тестовый диалог пользователя из `chat.test.url` и восстанавливается после
  проверки. `chat.test.url` хранит тестовую ссылку; модуль продолжает читать
  только `chat.url`.
  Персональные ссылки не зашиваются в код. Каталог `Data/` уже исключён из Git.
- Существующий
  `Applier/src/main/java/com/seeker/applier/shared/ManagedBrowser.java`:
  запуск или подключение к управляемому браузеру. Переиспользовать напрямую,
  без копирования и без переноса общего браузерного кода в рамках этой задачи.
- `Tools/src/main/java/com/seeker/tools/LinkedInJobAvailability.java`:
  общий HTTP-запрос и классификация LinkedIn-страницы, вынесенные из
  `LinkedInAvailabilityChecker`. `Check LinkedIn` и ChatEvaluator используют
  один оригинал. Общий класс не зависит от Applier, ChatEvaluator, JavaFX,
  базы и Jackson. Обе сборки подключают `Tools/src/main/java` через
  `add-source`. Массовые повторы, журнал и изменение статусов остаются
  в GUI-проверке. Для Tools не создаётся отдельный Maven-проект.
- JavaFX GUI: кнопка `GPT Eval` рядом с `Apply`, вызов модуля и отдельное окно
  с полным текстом возвращённого ответа. Для длинного текста достаточно
  стандартного многострочного текстового поля с прокруткой.
  Использовать существующий подход к фоновым операциям, чтобы ожидание
  не блокировало интерфейс. Работу со страницей и чтение настройки
  оставить в ChatEvaluator.

При подключении к GUI добавить каталог исходников ChatEvaluator в существующую
сборку `GUI/JavaFX/pom.xml`, как уже подключены исходники Applier.
GUI продолжает вызывать Java-класс напрямую. Запускать JAR как подпроцесс
из GUI не требуется. CLI — отдельный проверочный запуск того же модуля;
HTTP-сервис и фоновый сервер не создаются.

## Контракт CLI и общность с GUI

Команда из корня репозитория:

```text
java -jar ChatEvaluator/target/chat-evaluator.jar <vacancy-url>
```

Один URL соответствует одному вызову общего `run`. Ошибочные аргументы
обрабатываются до запуска браузера. Полный ответ выводится в stdout,
ошибки и диагностика — в stderr; кодировка UTF-8. Код `0` означает успешный
ответ, `1` — ошибку оценивания, `2` — ошибку аргументов.
Консольный вывод и код завершения принадлежат `main`; общий `run` возвращает
текст или выбрасывает исключение и не вызывает `System.exit`.

Использовать те же локальные файлы настроек и существующее свойство
`seeker.projectRoot`; по умолчанию корнем считается рабочая директория.
CLI не переопределяет профиль, селекторы, таймауты или правила завершения
ответа. Различия ограничиваются CLI-аргументами и консольным выводом,
а в GUI — выбором вакансии, фоновым вызовом и окном результата.

В общем коде не должно появиться ветвлений браузерного сценария по признаку
GUI/CLI. Сохраняется прямое переиспользование `ManagedBrowser` из Applier;
выделение отдельного общего модуля для этого пункта не требуется.

## Работа с диалогом

До подключения к управляемому браузеру выполнить один HTTP-запрос вакансии
через `LinkedInJobAvailability.fetch`, затем вызвать общий `classifyResponse`.
Только `available` разрешает переход к ChatGPT. `closed`, `unavailable`,
необходимость входа, сетевые ошибки и неожиданная страница завершают
оценивание ошибкой без отправки в чат. При HTTP 429 подключиться через
`ManagedBrowser`, открыть вакансию через `newBackgroundPage()` в том же
профиле и дождаться описания или признака закрытых заявок. Навигация
и ожидание разметки ограничены 30 секундами каждое; ожидание использует
таймер, а не кадры анимации. Общий классификатор получает HTTP-статус,
итоговый URL, HTML и видимый текст страницы. Для признака закрытия браузерная
проверка использует видимый текст, чтобы не учитывать скрытые шаблоны.
Временная вкладка закрывается при любом исходе. Только `available` позволяет
открыть/использовать диалог ChatGPT; повторный 429 и ошибки браузерной
проверки останавливают оценивание без отправки. ChatEvaluator не запускает массовый
`LinkedInAvailabilityChecker`, не повторяет запрос и не меняет базу вакансий.

Использовать вкладку с заданным диалогом, если она уже открыта в управляемом
браузере; иначе открыть указанный адрес. Работать именно с этим диалогом,
сохраняя его историю. После операции диалог и браузер остаются открытыми.
Другие вкладки не участвуют в оценке.

Для отправки дождаться единственной видимой и доступной кнопки
`button[type='submit']` и один раз вызвать её DOM-метод `click()`.
Проверка `disabled`, disabled fieldset и `aria-disabled` и сам клик выполняются
в одной JavaScript-задаче. Ожидание доступности ограничено 15 секундами и
не зависит от кадров анимации или вывода вкладки на передний план.
При ошибке действия отправки его не повторять.

Уже открытую вкладку не перезагружать перед каждым запросом. До ввода URL
дождаться загруженной истории и завершения предыдущего turn. Отправлять URL
одним нажатием штатной кнопки `button[type='submit']`; Enter и повторную
отправку после этого не выполнять.

Перед отправкой сохранить ключи turn и идентификаторы сообщений. В течение
15 секунд подтвердить очистку composer и появление нового user-сообщения
с точным URL, новым ID и новым turn после последнего известного turn.
Только после подтверждения отправки начинается ожидание ответа (180 секунд).
Ответ, его новый ID, текст и `complete` проверяются внутри подтверждённого
turn с тем же user ID. Рост общего количества ответов и чужой `complete`
не являются подтверждением. Неудача подтверждения отправки и таймаут
ответа сообщаются как разные этапы; автоматических повторов нет.

Через элементы страницы найти поле ввода, отправить URL и получить новый
ответ после завершения генерации. Конкретные селекторы и признак завершения
определить по реальной странице тестового диалога в первом пункте плана.
Перед любой проверочной отправкой сверить целевой адрес с тестовой ссылкой
пользователя. Рабочий диалог для отладки и проверок не использовать.
Предыдущий ответ и промежуточный текст не считать результатом нового запроса.

Ответ возвращается как текст без пересказа и дополнительной оценки другим
агентом. В GUI показывается весь полученный ответ в отдельном окне.
Специальная структура ответа, JSON и извлечение отдельных оценок сейчас
не нужны. На первом проверочном запуске достаточно увидеть исходный текст
ответа вне GUI.

Отдельное сохранение ответа и система асинхронных задач с последующим
получением результатов сейчас не нужны. Фоновый вызов в GUI служит только
для того, чтобы интерфейс не зависал во время ожидания.

Codex CLI, Codex Proxy и OpenAI API в этом потоке не используются.
Модуль не передаёт в чат оценки Seeker, резюме или дополнительные инструкции:
согласованный вход — только URL вакансии.

Автоматические тесты ограничены юнит-тестами без браузера и реальной сессии.
Живые проверки выполняются отдельно по указанию пользователя в тестовом
диалоге; автоматических интеграционных тестов с ChatGPT не должно быть.
Тестовый диалог с правилами и контекстом пользователь подготавливает заранее.

Живая проверка через JavaFX GUI из пункта 3 плана необязательна. Приёмка
подключения GUI включает ревью кода, сборку и подходящие имеющиеся
юнит-тесты; управление окном внешним инструментом не является обязательной
частью приёмки. Если такой инструмент не работает, это ограничение проверки,
а не подтверждение ошибки приложения. Ремонт инструмента управления окном
не входит в архитектуру и объём работ ChatEvaluator.

CLI из пункта 4 предназначен для тестирования и диагностики без JavaFX GUI
и внешнего инструмента управления окнами. Нужный живой проверочный вызов
выполняется через этот вход в тестовом диалоге. Тесты CLI изолируются от
реальной сессии; наличие CLI не добавляет автоматических интеграционных
тестов с ChatGPT.

## Неопределённости

Способ входа в ChatGPT в управляемом браузере пользователь отложил до живой
проверки. Сейчас не открывать страницу ради настройки входа и не писать
механизм автоматического логина. Если при живом запуске понадобится вход,
показать фактическую ситуацию пользователю и определить способ вместе с ним.

Пользователь предоставил отдельный тестовый диалог; его ссылка сохранена
локально в `chat.test.url`. Живой проверкой ещё не подтверждено, что диалог
получает достаточно данных о вакансии по одной LinkedIn-ссылке.

Если реальная проверка выявит препятствие, исполнитель показывает наблюдение
пользователю и ждёт решения. Самостоятельно переходить к передаче текста
вакансии, новому диалогу, API или другой схеме работы нельзя.
