# Требования ChatEvaluator

## Назначение

Дать пользователю дополнительную независимую оценку соответствия вакансии
перед подачей заявки. Оценку выполняет ChatGPT в существующем диалоге,
где уже есть контекст пользователя. Проверка запускается отдельным действием
и дополняет анализ Codex в Seeker.

## Согласованное поведение

- Запуск — по кнопке `GPT Eval` рядом с `Apply` в JavaFX GUI для выбранной вакансии.
  Один запуск отправляет одну ссылку на вакансию.
- Для тестирования и диагностики предусмотреть запускаемый JAR с минимальным
  CLI. GUI и CLI вызывают один и тот же код оценивания; контракт CLI описан ниже.
- GUI передаёт URL вакансии модулю. Настройку целевого диалога и взаимодействие
  с ChatGPT обрабатывает ChatEvaluator.
- До подключения к ChatGPT проверить доступность LinkedIn-вакансии тем же
  HTTP-запросом и классификатором, которые использует `Check LinkedIn`.
  Отправлять ссылку только при результате `available`. Недоступная вакансия
  (`unavailable`) и закрытые заявки (`closed`) останавливают оценивание.
  При 429, требовании входа, сетевой ошибке или неожиданной странице
  доступность не подтверждена: показать ошибку и не отправлять ссылку.
  Для одной оценки выполняется один запрос без повторов и без записи
  статусов/оценок в базу; поведение одинаково для GUI и CLI.
- Использовать браузер и Playwright с существующим `ManagedBrowser`.
  Если управляемый браузер закрыт, он запускается существующим механизмом.
  Живой прогон проводится в профиле, где пользователь вошёл в ChatGPT.
- Использовать существующий диалог по ссылке пользователя. В него отправлять
  только URL вакансии, без результатов текущего анализа Seeker и дописанного
  исполнителем промпта. Историю диалога сохранять.
- Получить новый ответ на отправленную ссылку после завершения генерации.
  Перед ожиданием ответа подтвердить новое user-сообщение с переданным URL
  и новым идентификатором; ответ и завершение должны относиться к его turn.
  Повторная оценка той же ссылки также требует нового сообщения. Если
  отправка не подтверждена, сообщить об этом отдельно, не возвращать старый
  ответ и не выполнять автоматическую повторную отправку.
  Перед ожиданием ответа подтвердить новое user-сообщение с переданным URL
  и новым идентификатором; ответ и завершение должны относиться к его turn.
  Повторная оценка той же ссылки также требует нового сообщения. Если
  отправка не подтверждена, сообщить об этом отдельно, не возвращать старый
  ответ и не выполнять автоматическую повторную отправку.
  Вернуть и показать весь текст ответа в отдельном окне, без сокращения
  и пересказа другим агентом. Длинный ответ должен быть доступен целиком
  с помощью прокрутки. Специальную структуру ответа ChatGPT не навязывать.
- Во время ожидания не блокировать JavaFX Application Thread.
- Диалог и браузер после завершения остаются открытыми.
- Оценка не запускает Applier, не заполняет и не отправляет заявку,
  не меняет статус вакансии или существующие оценки Seeker.

## Запускаемый JAR и минимальный CLI для проверок

Это обязательное расширение по пункту 4 плана. CLI нужен исполнителю для
проверки и диагностики того же сценария без управления JavaFX GUI.
Для обычной оценки вручную проще воспользоваться самим интерфейсом ChatGPT;
отдельный пользовательский продукт вокруг CLI не требуется.

- Сборка из корня репозитория: `mvn -f ChatEvaluator/pom.xml package`.
  Результат — `ChatEvaluator/target/chat-evaluator.jar`, запускаемый на Java 21
  или новее командой `java -jar ChatEvaluator/target/chat-evaluator.jar <vacancy-url>`.
- JAR включает необходимые runtime-зависимости. При запуске не требуются Maven,
  ручное составление classpath, JavaFX или jpy. Локальные настройки
  и существующий профиль браузера остаются внешними.
- Минимальный интерфейс — одна команда с позиционным аргументом URL вакансии.
  Синтаксис и параметр описываются в README; отдельная команда справки не нужна.
  Отсутствующий, лишний или начинающийся с `-` аргумент отклоняется до обращения
  к браузеру с кодом `2` и сообщением в stderr.
- При успехе stdout содержит весь исходный текст ответа без пересказа,
  сокращений, JSON-обёртки и служебных подписей. Ошибки и диагностика идут
  в stderr. Текстовый вывод — UTF-8.
- Коды завершения: `0` — ответ получен; `1` — ошибка оценивания; `2` — неверные
  аргументы. При ошибке не печатать старый или
  частичный ответ как успешный результат.
- Оба входа вызывают `ChatEvaluatorRunner.run(String vacancyUrl)`.
  Чтение настроек, `ManagedBrowser`, профиль и канал браузера, выбор диалога,
  отправка URL, селекторы, таймауты, ожидание нового законченного ответа
  и извлечение текста должны быть общими. Копировать эту логику для CLI нельзя.
- Различия ограничить получением URL и представлением результата: GUI получает
  URL выбранной вакансии и показывает ответ в окне через существующий фоновый
  вызов; CLI получает URL из аргумента и печатает ответ после завершения вызова.
- По умолчанию CLI запускается из корня репозитория. Для другой рабочей
  директории используется существующее JVM-свойство `seeker.projectRoot`.
  При одинаковом корне репозитория GUI и CLI используют одни настройки.
- CLI не запускает JavaFX и не требует инструмента управления мышью или
  клавиатурой. Управляемый браузер и Playwright остаются частью рабочего
  сценария; диалог и браузер после вызова остаются открытыми.
- Все проверочные отправки из CLI выполняются только в тестовом диалоге
  по общим правилам ниже. Автоматических тестов с реальной сессией не добавлять.

## Настройка диалога

Пользователь предоставил ссылку на конкретный диалог ChatGPT. Она сохранена
в `Data/chat_evaluator/config.properties`, ключ `chat.url`; модуль должен
использовать этот адрес. Это рабочий диалог для обычных оценок вакансий.

## Правила тестирования и живых проверок

- Все живые проверки, отладка селекторов и проверочные отправки выполняются
  только в отдельном тестовом диалоге, который создаёт пользователь.
  Рабочий диалог для тестовых сообщений не использовать.
- Ссылка на тестовый диалог предоставлена пользователем и сохранена в том же
  локальном файле под ключом `chat.test.url`. Модуль читает `chat.url`;
  наличие `chat.test.url` само по себе не переключает его на тестовый диалог.
- Для живого проверочного запуска временно указать значение `chat.test.url`
  в локальном `chat.url`, сохранив рабочее значение, и до отправки убедиться, что открыт
  именно тестовый диалог. После проверки восстановить рабочее значение,
  в том числе при ошибке.
  Отдельный режим тестирования в коде сейчас не требуется.
- Для проверки содержательной оценки пользователь заранее подготавливает
  тестовый диалог с нужными правилами оценки и контекстом. Модуль по-прежнему
  отправляет только URL вакансии. Проверка в пустом диалоге сама по себе
  не подтверждает качество оценки с контекстом пользователя.
- Автоматические тесты — только юнит-тесты без браузера, реальной сессии
  и отправок в ChatGPT. Интеграционные тесты с реальным диалогом не добавлять
  и не запускать, включая тестовый диалог.
- Живые проверки из плана выполняются отдельно по явному указанию пользователя,
  в пределах текущего пункта. Ревью кода само по себе не разрешает живой запуск.
- Живая проверка полного пути через GUI (пункт 3 плана) необязательна.
  Для приёмки подключения GUI достаточно ревью кода, успешной сборки
  и подходящих имеющихся юнит-тестов. Пропущенную или недоступную
  GUI-проверку явно отметить в отчёте; она не блокирует приёмку реализации.
- Ошибки инструмента управления окном не считать ошибками приложения.
  Если инструмент не позволяет провести GUI-проверку, прекратить попытку
  и восстановить временные настройки. Диагностика этого инструмента
  не входит в задачу ChatEvaluator.

## Вход в ChatGPT

Способ входа в ChatGPT в управляемом браузере пока не определён. По решению
пользователя разбираться с этим нужно тогда, когда вход понадобится для
живой проверки. До этого не реализовывать механизм логина. Если требуется
вход, сообщить пользователю фактическую ситуацию и согласовать действие.

## Границы первой реализации

Нужен один рабочий путь: выбранная вакансия → существующий диалог → новый
ответ → показ пользователю. Отдельное сохранение результатов, система
асинхронных задач с последующим получением ответа, пакетная обработка,
ретраи, восстановление, очереди, новые системы статусов и поддержка
нескольких вариантов чат-интерфейса не входят в задачу. Существующий механизм
фонового вызова GUI используется только для отзывчивости интерфейса.

CLI из пункта 4 — второй вход в тот же модуль для проверок. Сервис,
HTTP API, отдельная реализация оценивания, пакетные команды и новый
протокол ответа в этот пункт не входят.

Не добавлять код для воображаемых, предполагаемых или ожидаемых проблем.
Если обнаружилось реальное препятствие или для продолжения нужно изменить
согласованный сценарий, сначала сообщить пользователю факты и получить
его решение. Не придумывать запасной путь самостоятельно.

## Приёмка

Требуемое поведение описано ниже. Полный прогон через GUI из пункта 3 плана
необязателен; отсутствие такого прогона не означает, что реализация
не завершена. Подключение GUI принимается по ревью кода, сборке и подходящим
имеющимся юнит-тестам с указанием, какие проверки фактически выполнены.

- В отдельный тестовый диалог отправлена ровно ссылка на проверяемую вакансию;
  рабочий диалог не использовался для проверки.
- ChatGPT дал содержательную оценку по этой ссылке; одной проверки появления
  сообщения в поле ввода недостаточно для подтверждения работоспособности.
- Модуль получил новый законченный ответ, а не текст старого сообщения.
- При выполнении необязательной живой проверки GUI этот же путь проходит
  от нажатия `GPT Eval` рядом с `Apply` до показа полного ответа в отдельном
  окне. Пользователь может прочитать весь ответ с прокруткой и сверить
  его с ответом в чате.
- Форма подачи заявки не открывается, статус и оценки вакансии не меняются.
- После пункта 4 доступен запускаемый JAR с указанным контрактом CLI.
  GUI и CLI вызывают общий `run`; сборка, ошибки аргументов,
  потоки вывода и коды завершения проверены без реальных отправок.

Реализация идёт по [PLAN.md](PLAN.md), строго с остановкой после каждого пункта.
