# План реализации ChatEvaluator

## Обязательные остановки

**Пункты этого плана — границы исполнения и ревью. После выполнения КАЖДОГО
пункта исполнитель ОБЯЗАН остановиться.**

В отчёте указать номер выполненного пункта, изменения, проведённую проверку
и её фактический результат. Дальше ждать ответа пользователя: он решает,
проводить ревью, тестировать, исправлять или начинать следующий пункт.

**Не начинать следующий пункт без явного указания пользователя.** Одобрение
плана целиком, успешный тест, собственное ревью или отсутствие новых сообщений
не разрешают продолжение. Пункты нельзя выполнять параллельно или делать
следующий «заодно». После исправлений снова показать результат и остановиться.

Реализацию выполняет отдельный агент. До начала он читает `REQUIREMENTS.md`,
`ARCHITECTURE.md` и применимые `AGENTS.md`. Наличие исходников само по себе
не подтверждает завершение пункта: нужны предусмотренные им результаты.

Пункты 1, 2 и 4 относятся к обязательной реализации. Пункт 3 — необязательная
живая проверка через GUI. Её пропуск или невозможность выполнить её средствами
исполнителя не блокируют приёмку обязательных пунктов. Пункт 4 — новое
расширение для проверок через запускаемый JAR и общий с GUI код.

## Правила проверок

Все живые проверки по этому плану проводить только в отдельном тестовом
диалоге, который предоставил пользователь. Ссылка на него сохранена в
`Data/chat_evaluator/config.properties` под ключом `chat.test.url`. Рабочий
диалог не использовать для тестов и отладки.

Перед живой проверкой сохранить рабочее значение `chat.url` в локальном
`Data/chat_evaluator/config.properties`, временно установить в `chat.url`
тестовую ссылку из `chat.test.url`
и сверить адрес открытого диалога. После проверки восстановить рабочее
значение, в том числе при ошибке. Сам модуль отправляет только URL вакансии;
правила оценки и контекст в тестовом диалоге заранее подготавливает пользователь.

Автоматически запускать только юнит-тесты без браузера, реальной сессии
и отправок сообщений. Интеграционные тесты с реальным ChatGPT не добавлять
и не запускать даже в тестовом диалоге. Живой прогон — отдельная проверка
по явному указанию пользователя в рамках текущего пункта. Ревью кода
не предполагает запуск GUI или живого диалога.

После реализации пункта 4 для нужных проверочных вызовов без GUI использовать
CLI запускаемого JAR. CLI подчиняется тем же правилам тестового диалога.
Справка и ошибки аргументов проверяются без браузера и отправок; живые
прогоны не становятся автоматическим тестом после каждой правки.

Для подключения GUI обязательны ревью кода, успешная сборка и запуск
подходящих имеющихся юнит-тестов. Открытие окон, автоматические клики,
визуальная проверка и полный живой прогон из GUI относятся к необязательному
пункту 3 и не запускаются автоматически при ревью.

Если средство управления окном не позволяет выполнить проверку, прекратить
эту попытку, восстановить временные настройки и указать «GUI-проверка
не выполнена: ограничение инструмента». Это не результат теста приложения
и не основание объявлять GUI неисправным. Диагностика или ремонт инструмента
управления окном не входят в этот план.

Разрешение на GUI-проверку покрывает обычные клики и ввод в рамках
согласованного сценария и выделенного пользователем времени; подтверждение
каждого нажатия не требуется. По окончании этого времени или после остановки
пользователем управление прекращается и само не возобновляется.

## Пункты

### 1. Рабочий модуль без GUI и первая живая проверка

Рабочая ссылка уже сохранена в `Data/chat_evaluator/config.properties`,
ключ `chat.url`; тестовая ссылка — в `chat.test.url`. Для живой проверки
применить правила проверок выше.
Начать пункт по указанию пользователя агенту-исполнителю.

Реализовать минимальный Java-модуль с чтением локальной настройки адреса диалога
и входом `run(String vacancyUrl)`. Переиспользовать существующий
`ManagedBrowser`. На реальной странице тестового диалога определить нужные
элементы и признак завершения ответа; отправить в этот диалог одну ссылку
на вакансию, дождаться нового законченного ответа и вернуть весь его текст.

Вопрос входа в ChatGPT отложен до живого запуска. Если в используемом
браузере потребуется вход, сообщить пользователю фактическую ситуацию
и определить способ вместе с ним. Механизм логина заранее не реализовывать.

Проверить вызовом самого модуля без GUI в тестовом диалоге. В отчёте показать
URL проверенной вакансии, отправленное сообщение и полученный ответ;
подтвердить использование тестового диалога и восстановление рабочего
значения `chat.url`. Подтвердить, что ChatGPT
смог оценить вакансию по ссылке. Открытие браузера или отправка сообщения
без получения ответа не означают завершения пункта.

Если этот путь не работает, показать конкретное препятствие и остановиться
для решения пользователя. Не подменять URL текстом вакансии, не создавать
диалоги самостоятельно, не переключаться на рабочий диалог или API.

**ОСТАНОВКА. Показать результат пункта 1 и ждать решения пользователя.**

### 2. Подключение к JavaFX GUI

Начать только по явному указанию пользователя после ревью пункта 1.
Кнопка и представление результата уже согласованы ниже.

Подключить исходники ChatEvaluator к существующей сборке GUI. Добавить
кнопку `GPT Eval` рядом с `Apply` для выбранной вакансии, вызов готового модуля
и отдельное окно с полным текстом ответа и прокруткой. Логику работы с браузером и настройкой
диалога оставить в модуле. Использовать существующие механизмы GUI
для фоновых операций и сообщения об ошибке.

Собрать GUI. По коду проверить подключение действия, фоновый вызов, передачу
всего ответа в окно результата и обработку ошибок; при наличии подходящих
юнит-тестов запустить их. Запуск GUI и визуальная проверка не обязательны
для этого пункта. Живой прогон из GUI относится к необязательному пункту 3.
Сохранение результатов и отдельную систему асинхронных задач не добавлять.
Существующий фоновый вызов нужен только для того, чтобы ожидание ответа
не блокировало GUI. В чат по-прежнему отправляется только URL вакансии.
Уточнить README по фактической настройке и сборке на основании кода
и уже полученных результатов; для этого не требуется запускать GUI.

**ОСТАНОВКА. Показать результат пункта 2 и ждать решения пользователя.**

### 3. Необязательная живая проверка полного пути из GUI

**Статус: закрыт — необязательная GUI-проверка пропущена.**

Успешный полный прогон через GUI исполнителем не подтверждён. Это
не оставляет этот необязательный пункт открытым и не блокирует приёмку
обязательных пунктов. Дополнительных действий по пункту 3 в рамках текущей
реализации не требуется. Описание ниже сохранено для возможной отдельной
проверки в будущем.

Выполнять только по отдельному явному указанию пользователя после ревью
пункта 2. Этот пункт можно пропустить. В таком случае в отчёте указать,
что полный путь через GUI не проверялся; это не блокирует приёмку реализации.

Настроить тестовый диалог по правилам проверок выше. Выбрать другую вакансию
и запустить проверку кнопкой `GPT Eval` рядом с `Apply`.
Сверить отправленную ссылку, новый законченный ответ в этом тестовом диалоге
и весь текст в отдельном окне GUI. Убедиться, что интерфейс остаётся отзывчивым,
чат открыт, а статус и оценки вакансии не изменились.

В отчёте подтвердить, что использовался тестовый диалог, рабочее значение
`chat.url` восстановлено, и привести конкретный результат полного прогона
и оставшиеся наблюдаемые ограничения, если они есть. При необходимости
дополнить README подтверждёнными наблюдениями. Если проверка не состоялась,
не отмечать её как успешную или как выявленную ошибку приложения.
Не добавлять улучшения за пределами требований.

**ОСТАНОВКА. Показать результат пункта 3 и ждать решения пользователя.**

### 4. Запускаемый JAR и минимальный CLI для проверок

**Статус: запланирован, реализация не начата.**

Подготовить отдельную минимальную сборку `ChatEvaluator/pom.xml` с результатом
`ChatEvaluator/target/chat-evaluator.jar`, запускаемым через `java -jar`
на Java 21 или новее. JAR включает необходимые runtime-зависимости;
для его запуска не нужны Maven, ручной classpath, JavaFX и jpy.
Настройки и профиль браузера остаются внешними.

CLI нужен для тестирования и диагностики ChatEvaluator. В README прямо
указать это назначение: для обычной ручной оценки проще открыть сам ChatGPT.
Проверочный CLI-вызов должен позволять проверить тот же модуль без управления
окном JavaFX и без внешнего помощника мыши или клавиатуры.

Использовать существующий `main(String[] args)` как тонкий вход в
`ChatEvaluatorRunner.run(String vacancyUrl)`. GUI продолжает вызывать этот же
`run` напрямую. Чтение настроек, `ManagedBrowser`, профиль, выбор диалога,
отправка URL, селекторы, таймауты, ожидание завершения и извлечение ответа
должны оставаться общими. Не создавать копию оценивания для CLI и не запускать
CLI-процесс из GUI. Оригинальный `ManagedBrowser` подключить к сборке напрямую,
без копирования исходников и без нового общего модуля.

Зафиксированный микро-API:

- `java -jar ChatEvaluator/target/chat-evaluator.jar <vacancy-url>` — один вызов,
  полный исходный ответ в stdout, UTF-8.
- `--help` — справка и код `0`, без чтения настроек и запуска браузера.
- Неверные аргументы — сообщение и usage в stderr, код `2`, без браузера.
- Ошибка оценивания — сообщение в stderr и код `1`; успех — код `0`.
- Служебные сообщения не смешиваются с ответом в stdout.
- По умолчанию запуск из корня репозитория; для другой рабочей директории
  используется существующее JVM-свойство `seeker.projectRoot`.

Собрать JAR и GUI, запустить подходящие юнит-тесты без реальной сессии.
Проверить запускаемый артефакт командами справки и ошибочных аргументов,
их stdout/stderr и коды завершения. Общность GUI и CLI проверить по вызову
одного `run` и отсутствию дублирования логики. Если нужен живой проверочный
запуск, выполнить его через JAR только в тестовом диалоге по общим правилам,
без автоматических повторов и без обязательного запуска JavaFX GUI.

Обновить README фактическими командами сборки и запуска, назначением CLI
для тестирования, правилами тестового диалога и результатами проверки.
Отдельный сервис, HTTP API, очереди, пакетные операции и новый формат
ответа не добавлять.

**ОСТАНОВКА. Показать результат пункта 4 и ждать итогового ревью пользователя.**
