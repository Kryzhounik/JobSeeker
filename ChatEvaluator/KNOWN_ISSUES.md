# Известные дефекты ChatEvaluator

Зафиксированы по сообщениям пользователя 2026-10-16 и чтению текущего кода.
Первоначально исправления были отложены до реализации пункта 4
(запускаемый JAR и CLI). Пункт 4 завершён; 2026-10-17 пользователь отдельно
поручил проверить доступные части пункта 3 через CLI и исправить оба дефекта.

Оба дефекта относятся к общему `ChatEvaluatorRunner.run(String vacancyUrl)`.
Исправления применяются одинаково к GUI и CLI.

## Проверка вакансии при HTTP 429, 2026-10-19

По поручению пользователя HTTP 429 больше не останавливает оценивание
немедленно: выполняется одна дополнительная проверка вакансии в фоновой
вкладке управляемого браузера с существующей сессией. Вкладка закрывается
при любом исходе. В ChatGPT ссылка отправляется только после `available`;
закрытая/недоступная вакансия, повторный 429 и ошибки проверки останавливают
вызов. Код общий для GUI и CLI. Живой прогон этого пути не выполнялся.
Существующие 14 юнит-тестов и изолированная `LinkedInAvailabilitySmoke`
прошли; JAR собран и GUI скомпилирован. Эти проверки не подтверждают
браузерные селекторы на реальной странице LinkedIn.

Пользователь сообщил о таймауте 30 секунд в браузерной проверке. Старый
текст ошибки не различал навигацию и ожидание описания, поэтому точный
этап по скриншоту не установлен. В проверке обнаружены отличия от коллектора:
отсутствие эмуляции фокуса для фоновой вкладки и ожидание только трёх
селекторов классической разметки. Добавлены эмуляция фокуса, поддержка
контейнеров и маркеров описания, которые использует коллектор, исключение
видимых индикаторов загрузки, распознавание формы входа и отдельная ошибка
таймаута с этапом и текущим URL. HTTP-классификация не получает расширенные
правила для видимого текста. Какое из этих отличий вызвало исходный таймаут,
по прежнему сообщению ошибки не установлено.

После получения ссылки пользователя выполнен один целевой живой вызов
исправленной браузерной проверки для вакансии `4477717986` через код
собранного JAR: результат `available`, таймаута нет. Проверочная фоновая
вкладка закрыта; обращений к ChatGPT и отправок сообщений не было.
Существующие 14 юнит-тестов и `LinkedInAvailabilitySmoke` прошли; JAR
пересобран, GUI с общим кодом скомпилирован.

## Повтор CE-002: таймаут клика, 2026-10-19

На скриншоте пользователя кнопка `button[type='submit']:visible` найдена,
но `Locator.click` истёк через 15 секунд на проверке `visible, enabled and
stable`, до самого клика. Какая именно проверка не завершилась, лог не
устанавливает. В частности, проверка стабильности зависит от кадров
анимации, которых может не быть у фоновой/свёрнутой вкладки; это возможная
причина, а не подтверждённый диагноз данного случая.

В общем сценарии GUI/CLI ожидание заменено на проверку единственной видимой
и доступной кнопки без кадров анимации и один DOM-вызов `button.click()`.
`disabled` (включая fieldset) и `aria-disabled` проверяются перед кликом
в той же JavaScript-задаче. Ожидание кнопки ограничено 15 секундами.
После клика остаётся отдельное подтверждение нового user-сообщения;
повторной отправки при ошибке или отсутствии подтверждения нет.

Живой прогон этого изменения не выполнен; устранение наблюдавшегося
таймаута на реальной странице пока не подтверждено.
Существующие 14 юнит-тестов прошли; они проверяют сопоставление сообщений
и ответов, а не DOM-клик. JAR собран, GUI с общим исправленным кодом
скомпилирован без запуска приложения.

## Исправления 2026-10-17

- CE-001: общий счётчик ответов исключён из определения результата. До
  отправки сохраняются ID сообщений и ключи turn; после одного Submit
  подтверждается новое user-сообщение с точным URL и новым ID. Ответ,
  его новый ID и `complete` проверяются только в этом turn. Повтор одного
  URL требует нового user ID и turn. Открытая вкладка не перезагружается.
- CE-002: вместо Enter выполняется один клик штатной кнопки
  `button[type='submit']`, найденной по фактической разметке. Очистка composer
  и новое user-сообщение подтверждаются отдельно, в течение 15 секунд.
  При неподтверждённой отправке нет ожидания ответа в течение 180 секунд
  и нет повторного действия отправки. До ввода URL ожидается готовность
  истории и завершение предыдущего turn.
- Добавлены 14 изолированных JUnit-тестов без браузера и сессии; все прошли.
  JAR собран, GUI с тем же общим кодом скомпилирован.
- Старая версия CLI воспроизвела CE-002: URL остался в composer, новых
  user-сообщений не было, stdout пустой, код 1 по таймауту. Точную причину,
  по которой приложение не приняло Enter, этот прогон не устанавливает.
  Исходный возврат старого ответа CE-001 в этом прогоне не повторился.
- После исправления выполнены два отдельных живых CLI-вызова с одной и той
  же ссылкой `https://www.linkedin.com/jobs/view/4467618096/` только в тестовом
  диалоге. Оба создали новые user ID, assistant ID и turn; оба вернули код 0
  с пустым stderr. Полный stdout совпал с текстом своего завершённого ответа
  (211 и 290 символов). Composer очищен. Рабочая конфигурация восстановлена
  побайтово после каждого вызова. В тестовый диалог добавлены ровно два
  сообщения; автоматических интеграционных тестов не добавлено.
- В обоих ответах ChatGPT сообщил о LinkedIn 429 и вернул `UNCERTAIN`.
  Это ограничение получения описания вакансии; подстановка текста вакансии
  или изменение согласованного входа не выполнялись.

Оба дефекта исправлены в общем коде; идентификация нового ответа и отправка
подтверждены указанными юнит-тестами и целевыми живыми вызовами.

Ниже сохранены исходные наблюдения и анализ до исправления.

## CE-001. Возвращается ответ на предыдущую вакансию

**Наблюдение пользователя.** После нажатия `GPT Eval` браузер открылся,
новый URL был отправлен, но модуль сразу показал ответ по предыдущей вакансии.

**Что видно в коде.** В `ChatEvaluatorRunner.java` перед отправкой сохраняется
только `assistantMessages.count()` (строки 68–71 на момент записи).
В цикле любой рост этого общего счётчика означает `sawNewAnswer = true`;
последний assistant-блок считается ответом текущего вызова (строки 80–91).
Затем проверяются `complete` у его turn и стабильность текста (строки 93–106).
Подтверждение нового сообщения пользователя, его ID и связь с текущим
URL отсутствуют. Маркер `complete` может корректно относиться к старому turn.

**Вероятный механизм, пока не доказанный воспроизведением.** После
`navigate(... DOMCONTENTLOADED)` код ждёт только видимости поля ввода.
Это не подтверждает завершение загрузки истории. Если старые assistant-блоки
появятся после снятия `priorCount`, они будут приняты за новый ответ.
Стабильный старый текст с `complete` удовлетворяет текущему условию возврата.
Предыдущий успешный единичный прогон этот сценарий не исключает.

**Направление исправления после пункта 4.**

- Перед отправкой подтвердить готовность именно выбранного диалога
  и зафиксировать идентификаторы уже загруженных сообщений/turn.
- После отправки дождаться нового сообщения пользователя с переданным URL
  и новым идентификатором, затем привязать ожидание к его turn.
- Получать assistant-ответ только этого turn. Его идентификатор не должен
  совпадать с ранее существовавшими ответами; завершение проверять внутри
  этого же turn. Рост общего счётчика и общий последний блок не использовать
  как доказательство принадлежности ответа запросу.
- Учесть повторную оценку того же URL: совпадения текста ссылки недостаточно,
  нужен новый идентификатор сообщения/turn.

В ранее наблюдавшейся разметке доступны `data-turn-key` и
`data-chatgpt-search-message-ids`. Их связь с новым запросом и точные селекторы
нужно подтвердить при целевой диагностике через CLI, не подставлять наугад.

## CE-002. URL остаётся в поле ввода, затем происходит таймаут

**Наблюдение пользователя.** При следующем запуске URL появился в поле чата,
но отправки не произошло; вызов завершился по таймауту.

**Что видно в коде.** После `fill(vacancyUrl)` вызывается `press("Enter")`
(строки 70–71), после чего сразу начинается ожидание ответа. Код не проверяет
готовность отправки, появление нового сообщения пользователя или принятие URL
чатом. Поэтому неотправленный запрос приводит к общему таймауту ожидания
assistant-ответа.

По документации используемого Playwright 1.62.0 `Locator.press` фокусирует
элемент и посылает события клавиатуры. Успешное выполнение этого вызова
само по себе не подтверждает принятие сообщения приложением ChatGPT.

**Причина непринятой отправки пока неизвестна.** Нужно проверить фактическое
состояние чата и отправки. Возможна связь с CE-001: если первый вызов вернул
старый ответ раньше времени, ChatGPT мог ещё генерировать настоящий ответ,
когда пользователь запустил второй вызов. Также требует проверки готовность
обработчиков ввода после навигации. Это гипотезы, не установленная причина.

**Направление исправления после пункта 4.**

- Подтвердить готовность composer и штатного действия отправки; учитывать
  уже идущую генерацию, чтобы не считать такой чат готовым к новому запросу.
- По фактической разметке выбрать одно надёжное действие отправки
  (например, доступную кнопку Send). Простая замена Enter кликом без проверки
  результата недостаточна. Не выполнять Enter и дополнительный клик вслепую.
- После действия отдельно дождаться подтверждения нового сообщения
  пользователя с нужным URL и новым ID. Только затем ожидать ответ этого turn.
- Если отправка не подтверждена, сообщить именно об этом этапе, а не ждать
  общий таймаут ответа. Не добавлять слепые повторы: сообщение может быть
  принято с задержкой, и повторная отправка засорит историю.

## Порядок дальнейшей работы

Сначала завершить пункт 4 и остановиться по правилам плана. Возврат
к исправлению этих дефектов — отдельная последующая работа.

Целевая последовательность общего вызова:

`готовый диалог → отправка URL → подтверждённое новое user-сообщение → ответ его turn → завершение этого ответа`.

Сохранить один общий сценарий GUI/CLI; очереди, автоматические ретраи,
отдельные фоновые системы и новые реализации оценивания не требуются.

При исправлении предусмотреть изолированные регрессионные проверки:

- Поздно появившийся старый завершённый ответ не возвращается как новый.
- Пока новый ответ генерируется, старый `complete` не завершает вызов.
- Повтор одного URL всё равно требует нового сообщения/turn.
- Заполненный composer без подтверждённой отправки не считается запросом,
  на который уже ожидается ответ; автоматической повторной отправки нет.

Нужные живые проверки после пункта 4 проводить через CLI только в тестовом
диалоге. Постоянные интеграционные тесты с реальной сессией не добавлять.
